# 产品案例：将路线采集需求转化为本地研究工具

我在这里整理工具的使用场景、设计思路与当前实现，说明我如何将研究中的采集需求转化为可操作的功能。

## 用户与问题

目标用户是需要批量采集路线数据的旅游管理、GIS 和交通地理研究者。核心任务不是获得一次导航结果，而是按研究计划，在多个客源地、目的地与日期之间获取可核查的数据。

需要解决的问题包括：重复输入地点、分散记录结果、去返程混淆、遗漏实际采集时间，以及失败记录难以追踪。

## 我与 AI 的分工

我负责提出研究需求、设计原型框架和规划功能，将地点、时间、方向与导出要求组织为具体任务。AI Agent 完成程序实现，我将工具用于实际研究数据采集。

## 当前方案与取舍

| 决策 | 对应功能 | 取舍与边界 |
| --- | --- | --- |
| 以批量任务组织查询 | 地点导入、任务配置、计划执行 | 需要先核对输入，不能用大规模任务代替试采 |
| 分开管理去程与返程 | 方向配置与路线明细 | 两个方向分别查询，不假设耗时对称 |
| 保留真实时间 | 每条请求的时间记录 | 计划时间不等于所有路线的共同观测时点 |
| 将异常作为数据质量问题 | 状态查看、失败重试、质量导出 | 请求失败和缺测不能直接作为不可达结论 |
| 采用本地服务和浏览器界面 | 本机 API、SQLite、浏览器交互 | 不依赖公共服务器，但电脑必须保持运行 |
| 分离模拟与真实查询 | mock / amap 提供器 | 模拟用于操作验证，不支持真实交通结论 |

这些设计首先服务于我自己的研究需求；面向其他研究者的独立试用与验证，是我下一步要补充的工作。

## 实际使用中的体会

研究中的采集往往不是查完一批路线就结束，而是需要在不同日期和时段重复执行。对我来说，工具的价值在于把地点、方向和时间安排放进同一套流程，采集结束后还能回看每条记录的状态与实际请求时间，再整理成后续分析所需的数据。

截至目前，实际采集累计完成 **23,986 次 API 请求，首次请求成功率 100%**。这是已完成任务的历史统计，原始日志未公开，不能据此推断其他网络或账户条件下的表现。

相比只看最终汇总，保留采集过程更方便核对数据是否符合研究要求。至于具体节省了多少时间，还需要通过同规模的人工与工具操作对照来衡量。

## 可检查的产品能力

- 使用少量模拟点位完成导入、任务创建、结果核对与导出。
- 检查坐标缺失、错误映射和重复编号等输入问题。
- 从导出记录核对路线方向、实际请求时间和结果状态。
- 结合自动化测试检查异常、任务恢复与研究数据导出行为。

自动化测试、模拟试采、真实地图调用和历史研究成果是四种不同证据，不应互相替代。

## 我的下一步计划

我计划继续补充以下验证：

- 记录研究者试用任务与问题，验证其他研究者能否独立完成操作。
- 建立人工与工具的同规模计时对照，记录配置、采集和核查耗时。
- 按首次请求、重试和最终任务结果分别统计指标，并保留可脱敏的汇总。
- 整理版本变更前后的问题、设计调整和验证结果。
